# Changelog

## Version 5.2.0 — 2026-08-21 — Admin hub media picker fixes + Documentation link

Patch release fixing broken media upload buttons on hub screens and a broken/warning-prone external Documentation link.

### Fixes

- **Media picker on Season Content / People, Places & Partners:** `wp.media` and its click handler were only enqueued on the exact Dashboard hook, CPT edit screens, the Season Builder tab, and Display Options — never on the Season Content or People, Places & Partners hub pages, even though both render full in-page CPT editors with "Select Image"/"Select Logo"/"Select Banner" buttons. Broadened the admin asset loader to match any StageKitWP admin screen.
- **Board Member photo picker:** Board Member uses its own dedicated button and JS file (`board-member-media.js`), separate from the shared media-button handler, and was gated strictly to `post.php`/`post-new.php`. Broadened its enqueue check to also load on any StageKitWP hub screen.
- **Documentation submenu:** using a raw external URL as the `add_submenu_page()` slug is unreliable — depending on whether a callback is registered, WordPress core either rebuilds it into a broken internal link, or runs `file_exists()` against the full URL (which throws a visible PHP warning under `open_basedir` restrictions on some hosts). Replaced with the standard, robust pattern: a normal internal page that redirects to the GitHub wiki on its `load-` hook, before any output is sent.

- `includes/stagekitwp-core-admin-menu.php`
- `cpt/stagekitwp-core-cpt/board-members.php`

## Version 4.6.14 — 2026-08-04 — Fix: review_align not applied to rating/comment

Fixes a bug where `review_align` (Per Show / Per Show Slider modes) only visibly moved the name/date meta line — the star rating and comment text stayed centered no matter what alignment was selected.

### Root cause

The plugin's global `assets/css/shortcodes.css` stylesheet has legacy rules hardcoding `.tm-rating` and `.tm-comment` to `text-align:center`. These rules have higher specificity/appear later than the per-instance `.tm-review-align-*` rule on the parent `.tm-per-show-review`, so `text-align` did not inherit down to the rating/comment children as expected.

### Fix

Added explicit per-instance CSS re-asserting the review's own alignment directly on `.tm-rating`, `.tm-comment`, and `.tm-meta` for each of `tm-review-align-left`, `tm-review-align-center`, and `tm-review-align-right` (covers `alternating` and `alternating_lr` too, since both resolve to one of these three classes per review). Verified via `inspect_design` and screenshot across `classic` and `overlay` layouts — rating stars, comment, and meta now move together with each review's alignment.

## Version 4.6.12 — 2026-08-04 — Fix: Spotlight layout image size

Fixes a bug where `[tm_testimonials layout="spotlight"]` did not honor the configured `image_height` (and, in the `image_position="top"` banner variant, effectively ignored `image_width` too by stretching full-bleed regardless of the image's aspect ratio).

### Root cause

The spotlight grid used `align-items:stretch` with `.tm-testimonial-media { height:100%; min-height:Xpx }`. Because the media column was stretched to match the height of its sibling review-text column, a short `image_height` was overridden whenever the review text ran long enough to make that row taller — the image rendered taller than requested instead of at the exact configured height.

### Fix

- `.tm-testimonial-media` in spotlight layout is now a fixed box at exactly `image_width` x `image_height` for left/right/center positions (grid `align-items` changed from `stretch` to `center`, image no longer stretches to fill the row).
- The `image_position="top"` banner variant keeps its intentional full-card-width look, but height is now capped at exactly `image_height` instead of drifting with content length.
- Verified across grid, per_show, and per_show_slider modes with `layout="spotlight"` at multiple `image_width`/`image_height` combinations via `inspect_design`.

- `includes/shortcodes/testimonials-shortcode.php`

## Series summary: 4.5.12 – 4.5.18 — 2026-07-05 — Tickets overhaul + critical live-site fix

This batch of patch releases completed a full overhaul of the `[tm_tickets]` shortcode and fixed a critical regression that suppressed all shortcode styles on live sites.

### Key changes at a glance

| Version | Change |
|---|---|
| 4.5.12 | `[tm_landingpage]` hero banner, heading size, cast dark mode, cast typography |
| 4.5.13 | `[tm_tickets]` Get Info button — replaced invalid nested `<a>` links in all 5 layouts |
| 4.5.14 | Spotlight: show images on tiles (4:3), responsive cast grid fix |
| 4.5.15 | Spotlight: full-width horizontal cards (reverted in 4.5.16) |
| 4.5.16 | Spotlight: N equal columns matching banner width; `--tm-spotlight-count` CSS var |
| 4.5.17 | Spotlight `object-fit:contain`; dark/light toggle moved to vars-only patcher path |
| 4.5.18 | **Critical:** `headers_sent()` guard removed from `tm_add_shortcode_inline_style()` |

### Critical fix detail (4.5.18)
`headers_sent()` returns `true` as soon as any HTML output starts. On live WordPress sites this is always the case by `the_content` time, silently discarding every shortcode `<style>` block. All `--tm-tk-*`, `--tm-lp-*`, and other CSS custom properties were undefined, causing black tiles and invisible text. Removed the guard; `<style>` in `<body>` is valid HTML5.

### Tickets layout summary (post-4.5.13)
- **banner**: ticket buttons + underline Get Info below each
- **minimal**: row + pill Get Info below each row
- **cards**: card is a `<div>` (not `<a>`); footer holds Get Tickets + Get Info as sibling links
- **table**: Get Info beside Get Tickets in the actions cell
- **spotlight**: `<div>` tile-wrap holds ticket `<a>` card + Get Info sibling; N equal columns via `--tm-spotlight-count`; 4:3 `object-fit:contain` images

## Version 4.6.0 — 2026-07-05 — Production release: Image & Banner Size Guide

Production release bump covering the 4.5.18–4.5.23 patch series plus the new image documentation.

### What’s new: Image & Banner Size Guide

A new **Image & Banner Size Guide** section has been added to the Instructions page (`Theatre Manager → Instructions`). It covers every image field in the plugin with optimum dimensions, minimum sizes, format recommendations, aspect ratio notes, and per-shortcode context.

#### Show Poster (`_tm_show_sm_image`)
- **Recommended:** 800 × 1200 px (2:3 portrait)
- **Minimum:** 600 × 900 px
- Appears in 5 shortcodes across 7 contexts. `[tm_landingpage]` hero shows the full image at natural size (`object-fit:contain`); card/programme/minimal layouts use `object-fit:cover` within a fixed frame. `[tm_tickets]` cards use a 2:3 frame; spotlight tiles use 4:3 (`object-fit:contain`, letterboxed). `[tm_season_shows]` spotlight and cards use a 4:3 frame.

#### Season Front Image (`_tm_season_image_front`)
- **Recommended:** 900 × 1200 px (3:4 portrait)
- Displayed in `[tm_seasons]` 16:9 hero (`object-fit:contain`). Used as fallback in `[tm_tickets]` spotlight hero when no Website Banner is uploaded.

#### Season Website Banner (`_tm_season_social_banner`)
- **Recommended:** 1920 × 600 px (~16:5 landscape)
- **Minimum:** 1200 × 375 px
- Served at `full` WP size. Used as: `[tm_season_shows]` full-width strip (220 px height, `background-size:cover`); `[tm_tickets]` spotlight hero (full-width, `object-fit:cover`, min-height 280 px, preferred over front image); `[tm_seasons]` 16:9 hero (preferred over front image); `[tm_landingpage]` season banner strip (hero + programme layouts, full-width, height auto).

#### Cast Photo (`_tm_cast_picture`)
- **Recommended:** 600 × 800 px (3:4 portrait)
- Displayed in `[tm_landingpage]` cast grid: 3:4 frame, `object-fit:contain`. Card width varies by column count.

#### Board Member Photo (`_tm_photo`)
- **Recommended:** 400 × 400 px (square) or 400 × 533 px (portrait)
- Grid: circular 120 × 120 px, `object-fit:cover`. List: 64 × 64 px circle. Table: 44 × 44 px circle. Spotlight: 3:4 portrait frame, `object-fit:cover`.

## Version 4.5.20 — 2026-07-05 — Fix: all shortcode colours black when Display Options saved with empty pickers

### Root cause

`tm_sanitize_css_color( get_option( 'key', '#default' ) )` has a subtle failure mode:

1. Admin opens Display Options, clears a colour picker, saves — option is stored as `''` in the database.
2. On the next page load, `get_option( 'key', '#default' )` returns `''` (the stored empty string), **not** `'#default'` (which is only used when the option row does not exist at all).
3. `tm_sanitize_css_color( '' )` returns `#000000` (its `$fallback` default).
4. The CSS custom property is set to `#000000` — black — for every cleared picker.

This made the entire shortcode render black-on-black when Display Options had ever been opened and saved on a live site, even if the pickers were left empty intentionally to inherit defaults.

### Fix

Changed all shortcode light-mode colour option reads to the **raw-first pattern**:

```php
// Before (broken):
$bg = tm_sanitize_css_color( get_option( 'tm_tickets_bg_color', '#f8f9fa' ) );

// After (fixed):
$bg = tm_sanitize_css_color( get_option( 'tm_tickets_bg_color', '' ), '#f8f9fa' );
```

The real default is now the second argument to `tm_sanitize_css_color()` (its `$fallback` param), which it returns when the input is `null` or `''`. `get_option()` always gets `''` as its own default, so it returns `''` for both "not set" and "saved as empty" — both cases fall through to the real default.

Dark-option reads (where empty means "use generic theme token") pass `''` as the fallback to preserve that semantic: `tm_sanitize_css_color( get_option( 'key', '' ), '' )` — returns `''` when the picker is empty, which is the correct signal to the dark-mode CSS block.

## Version 4.5.18 — 2026-07-05 — CRITICAL: shortcode styles silently suppressed on live sites

### Root cause

`tm_add_shortcode_inline_style()` in `includes/functions.php` contained:
```php
if ( headers_sent() || ( defined('REST_REQUEST') && REST_REQUEST ) ) {
    return;
}
```

`headers_sent()` returns `true` once any output has been sent to the browser. On live WordPress sites, by the time `the_content` runs (which is when shortcodes execute), HTML output has long since begun. `headers_sent()` therefore **always** returns `true` in this context, and every shortcode `<style>` block was silently discarded.

This was masked on the local Studio site because Studio's development server likely buffers output differently. The live site hit it immediately.

### Consequence

With no `<style id="tm-sc-tickets">` block on the page:
- `--tm-tk-bg`, `--tm-tk-text`, `--tm-tk-btn`, `--tm-tk-border` were never defined
- `background: var(--tm-tk-bg)` resolved to `transparent` — the live site's dark body showed through, making tiles appear black
- `color: var(--tm-tk-text)` resolved to the inherited text colour (`rgb(0,0,0)` — black on black, unreadable)
- This affected **all shortcodes** that use `tm_add_shortcode_inline_style()`, not just tickets

### Fix

Removed the `headers_sent()` check entirely. `<style>` elements in `<body>` are valid HTML5 and all browsers handle them correctly. The only remaining guard is the REST API check, which is still appropriate (no HTML page to inject into).

### Files changed
- `includes/functions.php`

## Version 4.2.3 — 2026-07-04 — Bio dark mode: JS patcher extended for CSS custom properties

### Bug fix — Theme 2.2.5, Plugin 4.2.3

Bio text in grid, list, and spotlight layouts was invisible in dark mode.
All previous fixes (PHP luminance validation, `!important` on child selectors)
were correct but couldn't help because the **JS dark mode patcher** was the
actual source of the problem.

**Root cause (definitive):**
The `applyDark()` patcher in `color-mode-switcher.js` calls `patchEl()` on
`.tm-board-members-block`, writing `background`, `color`, and `border` as
ordinary inline style properties. But `.tm-bm-card`, `.tm-bm-bio` and other
child elements use `var(--tm-bm-bg)` and `var(--tm-bm-text) !important` —
CSS custom properties. Because the JS never set `--tm-bm-text` on the block,
the `var()` call resolved to the **light-mode value** from the shortcode's
`<style>` block, regardless of what `color` the wrapper had.

**Fix (`color-mode-switcher.js` → Theme 2.2.5):**
- `patchEl()` extended with an optional `vars` object. When present, each
  key is set via `el.style.setProperty(k, v, 'important')`.
- `tagEl()` now initialises a `vars: {}` tracking object in `originals[idx]`.
- `patchEl()` records which custom properties it sets into `originals[idx].vars`.
- `restoreEl()` calls `el.style.removeProperty(k)` for each tracked var,
  returning the element to its stylesheet value on light-mode restore.
- In `applyDark()`, `.tm-board-members-block` elements now receive:
  ```js
  vars: { '--tm-bm-bg': scBg, '--tm-bm-text': scText, '--tm-bm-border': scBorder }
  ```
- Stale selector `.tm-board-members-grid h3, h4` updated to `.tm-board-members-block h3, h4`.
- Stale selector `.tm-board-member-card p` (old class name) replaced with
  the three new layout-scoped selectors covering `.tm-bm-bio` in grid, list,
  and spotlight.

## Version 4.2.2 — 2026-07-04 — Board Members dark mode: root cause fixed in luminance validator

### Bug fix

Bio text (and all board member text) was still dark (`#000000`) in dark mode
despite the 4.2.1 `!important` child-selector fix. Confirmed by `inspect_design`:
`--tm-bm-text` was resolving to `#000000` on `.tm-board-members-block` itself.

**Root cause 1 — `$safe_text` only rejected near-white, not near-black.**
`$safe_text` returned `$default` when `lum > 0.85` (near-white). But
`#000000` has luminance = 0, which passes `> 0.85` and was returned unchanged.
In dark mode, body text should be light — black text is just as wrong as white.
Fixed: `$safe_text` now rejects both extremes:
```php
return ( $lum > 0.85 || $lum < 0.04 ) ? $default : $value;
```
This fix also improves ticket dark mode resilience (same validator used there).

**Root cause 2 — board-members dark block placed before closures were defined.**
The block was emitted at line ~268 in `theme-integration.php`, before the
`$safe_surface`/`$safe_text` closures and `$d_safe_bg`/`$d_safe_text` were
defined (~line 319). It fell back to raw `$dark['surface_bg']` etc., which
are the Customizer values — `#000000` on this site.

Fixed: removed the early emit, added the board-members CSS block immediately
after `$d_safe_bg`/`$d_safe_text` are computed, using those validated values
as fallbacks.

**Root cause 3 — `$dark['border']` was also `#000000`.**
A near-black border is invisible on a dark card. Added an inline luminance
check: if the resolved border colour has lum < 0.04, fall back to
`rgba(255,255,255,0.15)` (a subtle white-alpha rule that works on any dark bg).

**Result (verified by screenshot):**
- Dark cards: `#1e1e1e` background
- Text: `#e0e0e0` — clearly readable
- Border: `rgba(255,255,255,0.15)` — subtle separator
- Bio text in grid, list, spotlight: inherits `--tm-bm-text` correctly

## Version 4.2.1 — 2026-07-04 — Board Members bio invisible in dark mode

### Bug fix

Bio text in `grid`, `list`, and `spotlight` layouts was not changing colour in
dark mode, making it invisible against the dark card background.

**Root cause:** The theme's `.entry-content p { color: var(--tm-body-text) }`
rule has higher specificity than the `.tm-bm-bio { color: var(--tm-bm-text) }`
rule when the shortcode is placed inside an `.entry-content` zone. In light
mode both vars resolve to dark text, so it wasn't noticed. In dark mode
`--tm-body-text` switches to light text correctly, but `--tm-bm-text` on
`.tm-board-members-block` also switches — the problem is that any `<p>` or
`<li>` tags produced by `wp_kses_post()` inside `.tm-bm-bio` match the theme's
`.entry-content p` rule first, ignoring the inherited `--tm-bm-text`.

**Fix:** Added explicit child-element rules with `!important` to all three
affected layout blocks:
```css
.tm-bm-card .tm-bm-bio p,
.tm-bm-card .tm-bm-bio li,
.tm-bm-card .tm-bm-bio span,
.tm-bm-card .tm-bm-bio a { color: var(--tm-bm-text) !important; }
```
Same pattern applied to `.tm-bm-list-row .tm-bm-bio` and
`.tm-bm-spotlight-card .tm-bm-bio`.

The `table` layout is unaffected — its bio lives inside `<td>` which already
has `color: var(--tm-bm-text)` directly on the `td` rule.

## Version 4.1.5 — 2026-07-04 — `tested` field fix; WP/PHP matrix in Other Notes

### Bug fix

**`tested` must be a single version string.** WordPress core does two things
with this field:
1. Displays it verbatim as "Compatible up to: {value}" in the modal header.
2. Runs `version_compare( get_bloginfo('version'), $api->tested, '<=' )` to
   determine whether to show a compatibility warning.

The previous value `"6.8.2, 7.0, 7.4"` would display literally (ugly) and
cause `version_compare()` to fail, potentially flagging the plugin as
incompatible on all sites. Fixed to `"6.8.2"` (the highest tested version).

The full compatibility list (WP 6.8 – 6.8.2, PHP 7.4 – 8.2) is now in the
**Other Notes** tab under the Requirements & Compatibility heading, where
it can list as many versions as needed without affecting the comparison logic.

Same fix applied to the `updater.php` inline fallback comment.

## Version 4.0.8 — 2026-07-04 — Spotlight hero text + tile hover blur

### Bug fixes

**Spotlight hero text invisible in light mode**  
`.tm-ticket-spotlight-hero` set `color:#fff` but without `!important`. The theme's
`main a { color: var(--tm-link) }` rule (which has equal or higher effective
specificity on anchor elements inside `main`) overrode it with `#0073aa` — the
same blue as the hero background. Result: label, title, and dates were all
blue-on-blue and completely invisible at rest (only readable if a hover state
changed something).  
Fix: added `!important` to the hero anchor `color` rule, and added explicit
`color: #fff !important` rules on `.tm-ticket-spotlight-hero-label`,
`.tm-ticket-spotlight-hero-title`, and `.tm-ticket-spotlight-hero-dates` so no
theme cascade can reach those elements.

**Spotlight tile hover causes text blur**  
`.tm-ticket-spotlight-tile:hover` applied `transform: translateY(-2px)` which
triggers GPU layer promotion and subpixel anti-aliasing on non-retina displays,
causing text to appear slightly blurry during and after the hover transition.  
Fix: removed the `translateY` from the tile hover rule. Hover feedback is now
provided solely by `box-shadow: 0 4px 14px rgba(0,0,0,.15)` — visually clear
without any compositing side-effects.

## Version 4.0.6 — 2026-07-04 — Tickets dark-mode: Customizer validation + explicit overrides

### Bug fixes

All 5 ticket layouts were still broken in dark mode despite the CSS-var-first
architecture added in 4.0.2. Two cascading root causes:

**Root cause 1 — CSS `var()` fallback doesn’t catch wrong values, only missing ones.**
The dark override block set `--tm-tk-bg: var(--tm-surface-bg, #1e1e1e)`.  The
fallback `#1e1e1e` only activates when `--tm-surface-bg` is *not defined at
all*.  On this site `--tm-surface-bg` is defined on `html.tm-dark-mode :root`
but holds the wrong value `#000000` (a Customizer misconfiguration), so the
CSS fallback never triggered and cards rendered black-on-black.

**Root cause 2 — Theme `main a { color }` override.**
The theme's dark-mode CSS sets `html.tm-dark-mode main a { color: var(--tm-link) }`.
Because all five ticket layout entry points are `<a>` elements (`.tm-ticket-btn`,
`.tm-ticket-card`, `.tm-ticket-min-row`, `.tm-ticket-spotlight-tile`), they
all inherited the link colour as their text colour, overriding the intended
body text colour.

### Fix (`includes/theme-integration.php`)

**PHP-level Customizer validation:**
Added `$safe_surface()` and `$safe_text()` closures that evaluate the
luminance of each saved Customizer dark value before using it:
- `$safe_surface`: rejects values with luminance < 4% (catches #000000 and
  near-blacks that would be invisible as a card background). Falls back to
  `#1e1e1e`.
- `$safe_text`: rejects values with luminance > 85% (catches near-white values
  that would be invisible on a dark background). Falls back to `#e0e0e0`.

This validation happens in PHP *before* any CSS is written, so the browser
never receives a colour that would produce invisible content.

**Explicit per-element colour overrides:**
Replaced the single `.tm-tickets-block` CSS-var redefinition with a full set
of explicit per-element `color:` and `background-color:` rules covering all
five layouts. These use the PHP-validated resolved values directly as hex
literals, not CSS var() chains, so there is no cascade path back to a bad
Customizer value.

Added explicit `color: {d_safe_text}` override on `.tm-ticket-btn`,
`.tm-ticket-card`, `.tm-ticket-min-row`, `.tm-ticket-spotlight-tile` to
neutralise the `html.tm-dark-mode main a { color: var(--tm-link) }` theme rule.
Buttons and CTAs continue to use `color: #ffffff` so white text on the accent
background is preserved.

## Version 4.0.5 — 2026-07-04 — Updater slug fix ("invalid plugin slug" resolved)

### Bug fix
Clicking **View details** on the Plugins screen showed "invalid plugin slug".

**Root cause:** WordPress normalises plugin slugs using `sanitize_title()`
before passing them to the `plugins_api` filter. `sanitize_title('Theatre Manager')`
returns `theatre-manager` (lowercase, hyphenated). Our updater was comparing
against `'Theatre-Manager'` (mixed-case, matching the folder name) so the slug
never matched and WordPress fell through to its own handler, which returned an
"invalid plugin slug" error because `Theatre-Manager` is not on WordPress.org.

**Fix (`includes/updater.php`):**
- Changed `slug` in `$transient->response[]` from `'Theatre-Manager'` to `'theatre-manager'`.
  This is what causes WP to build the correct `?plugin=theatre-manager` URL for the
  "View details" thickbox link.
- Changed `slug` in `$transient->no_update[]` to `'theatre-manager'` for consistency.
- Changed the `plugins_api` slug comparison from
  `'Theatre-Manager' !== \$args->slug` to
  `'theatre-manager' !== strtolower( \$args->slug )` so it matches case-insensitively
  regardless of how the slug arrives.
- Updated the manifest documentation comment slug to `'theatre-manager'` — the
  `slug` field in your server JSON should also use lowercase.

## Version 4.0.2 — 2026-07-04 — Tickets dark-mode: CSS-var-first architecture

### Summary
With no Display Options saved for the `[tm_tickets]` shortcode, dark mode was
broken on all layouts except the default banner. Root causes:

1. **`tm_tickets_enqueue_styles()`** embedded resolved PHP hex values directly
   in CSS selectors (`color: #333333`, `background: #0073aa`, etc.). The
   dark-mode `!important` overrides in `theme-integration.php` have equal
   specificity to the shortcode inline style, but the `tm-sc-tickets` body
   `<style>` tag fires *after* the head `tm-sc-integration-dark` block, so
   the light-mode values won the cascade even in dark mode.

2. **Banner renderer** injected `style="background:#0073aa;color:#fff;"` on
   every `<a.tm-ticket-btn>`. Inline styles have `(1,0,0,0)` specificity—
   no CSS `!important` can override them.

3. **`theme-integration.php` tickets dark block** was resolving PHP
   Customizer dark values at the time of rendering. If `tm_color_surface_bg_dark`
   had been saved as `#000000` (a misconfiguration on this local site), card
   backgrounds became black-on-black.

### Fix: CSS-var-first architecture

**`includes/shortcodes/tickets-shortcode.php`**
- `tm_tickets_enqueue_styles()` now declares all colour tokens as CSS custom
  properties on `.tm-tickets-block`:
  `--tm-tk-bg`, `--tm-tk-text`, `--tm-tk-btn`, `--tm-tk-btn-hov`,
  `--tm-tk-border`, `--tm-tk-font`, `--tm-tk-radius`, `--tm-tk-shadow`.
  Every selector rule references `var(--tm-tk-*)` instead of a hex literal.
- Removed the duplicate Display-Options dark override block from
  `tm_tickets_enqueue_styles()` — dark mode is handled entirely by
  `theme-integration.php`.
- `tm_tickets_render_banner()`: removed `style="background:...;color:#fff;"`
  inline attributes from all `.tm-ticket-btn` elements. Colour now comes from
  `var(--tm-tk-btn)` defined on the CSS class.
- `tm_tickets_render_spotlight()`: removed `style="background:...; "` and
  `style="color:...;"` from hero element and spotlight CTA. Added
  `.tm-ticket-spotlight-hero--color` modifier class for no-image fallback;
  added `.tm-ticket-spotlight-hero-dates` class.

**`includes/theme-integration.php`**
- Tickets dark-mode block rewritten to a single-selector CSS-var redefinition:
  ```css
  html.tm-dark-mode .tm-tickets-block {
      --tm-tk-bg:     var(--tm-surface-bg) !important;
      --tm-tk-text:   var(--tm-body-text)  !important;
      --tm-tk-btn:    var(--tm-link)       !important;
      --tm-tk-border: rgba(255,255,255,0.15) !important;
  }
  ```
  All element rules automatically update because they use `var(--tm-tk-*)`.
  Per-element exception overrides added only for elements outside the
  `.tm-tickets-block` scope (table row hover, badge backgrounds).
- Display Options dark pickers now override `--tm-tk-*` vars on the same
  selector block instead of per-element selectors.
- Removed dependency on resolved PHP Customizer hex values in the fallback
  path — no longer possible to get `#000000` card backgrounds from a
  misconfigured `tm_color_surface_bg_dark`.

## Version 4.0.1 — 2026-07-04 — Global link colour bleed + unscoped selector fix

### Summary
Two related bugs were causing link colours to bleed site-wide — into the

interface:

1. **Theme: bare `a { color }` global rule** in `tm_inject_customizer_css_variables()`

- Replaced bare `a { color: var(--tm-link); }` with a set of content-scoped

  This targets body-copy links only and leaves header/footer/admin-bar
  links unaffected.
- Added `.site-header .site-branding a`, `.site-header .custom-theme-logo-link`,
  and `.site-header .tm-logo-wrap` to the header text-colour override block
  so the logo link colour matches nav links instead of the body-link colour.

- Added `if ( is_admin() && ! is_customize_preview() ) { return; }` guard to
  `tm_inject_customizer_css_variables()` and `tm_output_dark_mode_css()` so

## Version 3.9.9 — 2026-07-04 — [tm_tickets] full visual overhaul + CSS delivery fix

The `[tm_tickets]` shortcode rendered as an unstyled list of plain links. Root
causes identified and fixed:

1. **CSS never reached the browser** — `wp_add_inline_style()` is silently
   ignored when called after `wp_head` has fired. Shortcodes run inside
   `the_content`, which is always after `wp_head`. Fixed by changing
   `tm_add_shortcode_inline_style()` to `echo` a deduped `<style id="tm-sc-*">`

   never invalidated. Changed to `THEATRE_MANAGER_VERSION`.

   (display, flex, padding, margin) making every HTML element depend on PHP

## Version 3.8.1 — 2026-07-04

### Fixed
- **Critical: unscoped CSS selectors in `theme-integration.php` broke CF7 labels
  and every other `label`, `li`, `span`, `strong` on the page in light mode.**
  The dark-mode shortcode override block generated CSS like:
  ```
  html.tm-dark-mode .tm-board-members-grid p, li, td, th, span, label, strong {
      color: #e0e0e0 !important;
  }
  ```
  CSS parses comma-separated selector lists independently, so bare tags like
  `label`, `li`, `span` with no prefix became **global** rules — applying
  `color: #e0e0e0 !important` to every matching element on the entire page
  regardless of mode. This made CF7 form labels near-white in light mode.
  Fixed by building the selector list with `array_map` so every tag is
  individually prefixed: `html.tm-dark-mode .tm-board-members-grid label`,
  `html.tm-dark-mode .tm-sponsor-card label`, etc.
- **CF7 `style.css` light-mode rules strengthened** with
  `html:not(.tm-dark-mode)` scope and `!important` to beat any stale
  plugin stylesheets.

## Version 3.7.21 — 2026-07-03

### Added
- **Theatre Manager Theme dark/light mode integration** (`includes/theme-integration.php`).
  When the Theatre Manager Theme is the active theme, shortcode output now
  participates fully in the site's dark/light toggle. Previously, the plugin's
  shortcodes baked Display Option colours as hardcoded `style="background-color:
  #hex; color: #hex"` inline attributes that neither CSS `!important` nor the
  theme's JS patcher could reliably override.

  **How it works:**
  - `tm_theme_is_active()` — lightweight static helper that checks the active
    stylesheet/template slug. Returns false when any other theme is active so
    the integration is completely inert on non-TM sites.
  - `tm_output_shortcode_theme_integration_css()` — hooked to `wp_head` at
    priority 20 (after the theme's own token block). Emits two `<style>` blocks:
    1. *Light-mode block*: scoped CSS custom property declarations
       (`--tm-sc-bg`, `--tm-sc-text`, `--tm-sc-border`, `--tm-sc-font`) per
       shortcode wrapper selector, sourced from Display Options settings.
    2. *Dark-mode block*: `html.tm-dark-mode` overrides for every shortcode
       wrapper class, pulling `surface_bg`, `body_text`, `heading_text`,
       `muted_text`, `link`, and `border` from the theme's Customizer dark
       tokens. Covers: board members, advertisers, sponsors, contributors,
       testimonials, seasons, shows, cast, auditions, awards, venues, tickets.
       Specific sub-selectors for `h1–h6`, `p`, `li`, `a`, table cells,
       season/slot/show/program headings, and venue cards are all included.
  - `tm_integration_js_data()` — hooked to `wp_enqueue_scripts` at priority 15.
    Injects `tmShortcodeDark` (dark palette object) and `tmShortcodeSelectors`
    (array of wrapper CSS selectors) as JS globals before the
    `tm-color-mode-switcher` script body so the JS inline-style patcher can
    include shortcode wrappers in its `applyDark()` / `applyLight()` cycle.
    This covers elements whose inline `style=""` attributes would beat CSS
    `!important` rules.
  - `theme-integration.php` is required in the main plugin file after core
    includes and runs only on the frontend (`wp_head` / `wp_enqueue_scripts`).

  **When the TM theme is NOT active**, the integration file loads but all its
  hooks return immediately — zero output, zero performance cost.

## Version 3.7.20 — 2026-07-03

### Fixed
- **[BUG] Duplicate `admin_enqueue_scripts` hook conflict.** Two separate
  functions (`tm_enqueue_admin_assets` and `tm_enqueue_admin_scripts`) were
  both hooked to `admin_enqueue_scripts` and both registered the `tm-admin-js`
  handle with different dependency arrays. WordPress silently discards the
  second `wp_enqueue_script()` call for a handle already registered, so
  `wp-color-picker` never loaded on the Display Options page (color pickers
  were non-functional). Merged into a single unified `tm_enqueue_admin_assets()`
  function that conditionally adds `wp-color-picker` as a dependency only on
  the Display Options page.
- **[BUG] Fragile relative path in `tm_enqueue_slick_slider_assets()`.** Used
  `plugin_dir_url(__FILE__) . '../assets/js/'` from inside `includes/` — path
  traversal works but breaks if the file is moved. Replaced with the
  `TM_PLUGIN_URL` constant.
- **[BUG] Orphaned `tm_register_header_text_color_options()`.** Registered
  global h1–h6 color settings under `tm_display_options` (a group with no UI
  page). The per-tab `tm_{tab}_h1_color … tm_{tab}_h6_color` settings in
  `tm_register_display_settings()` are the correct equivalents. Removed the
  orphaned function and its `admin_init` hook.

### Changed
- **[PERF] Swiper, Slick Slider, and PDF.js are now conditionally loaded.**
  Previously all three libraries were unconditionally enqueued on every
  frontend page load (~250 KB extra JS+CSS per page for unrelated pages).
  Each library is now only enqueued when its corresponding shortcode is
  actually rendered on the current page:
  - Swiper → `[tm_sponsor_slider]`
  - Slick  → `[tm_testimonials]`
  - PDF.js → `[tm_programs]`
  Each shortcode callback calls the enqueue function directly; guard checks
  (`wp_style_is` / `wp_script_is`) prevent double-registration.
- **[UX] Top-level `Theatre Manager` admin menu now opens a proper dashboard
  page.** Previously the main menu callback pointed to `tm_display_options_page()`,
  so clicking the top-level item opened Display Options (confusing). A new
  `tm_dashboard_page()` function renders a card-grid landing page with direct
  links to Season Builder, Display Options, Settings, Instructions, Regenerate
  PDF Previews, and Sample Pages.
- **`tm_sanitize_css_color()` helper expanded.** Now accepts `rgb()`/`rgba()`,
  `hsl()`/`hsla()`, and CSS named colors / keywords (`transparent`,
  `currentColor`, etc.) in addition to hex values. Invalid values still fall
  back to the `$fallback` parameter.

### Fixed (metadata)
- `Requires PHP:` header in `theatre-manager-plugin.php` was blank. Set to
  `7.4` to match the theme's stated minimum.
